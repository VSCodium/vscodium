# PRD 骨架 · `docs/PRD-<代号>.md`

`<尖括号>` 为占位;引用块是写作指引,**写完删掉指引**。示例里的 `docs/PRD-A.md` / `docs/PRD-B.md` 这类具体文件名也是占位——它们在本 repo 里没有对应文件,写作时替换成宿主 repo 的真实 PRD 名。全篇不出现技术方案(表/端点/库/里程碑)。
规模参考:**160–380 行**。范围(§1 目标/非目标)约占 1/4,需求条目(§3)约占 1/2;领域语言、场景与决策只留能改变理解的内容,不为凑篇幅扩写。

**架构约定(全篇按此写)**:§0–§6 是**终局蓝图**——目标写终局结果,需求条目写完整能力,一条都不因「这期做不完」提前砍掉或写小。**交付节奏只出现在 §7**,等全局盘完之后一次给出,并逐条标出「终验期」= 整条需求算完成的那一期。跨期需求的终验期要在三处齐:§7.3、该需求 SPMS `description` 开头的终验块、`acceptanceCriteria` 逐行 `[P#]` 前缀。

## 0. 一句话

<一句话说清：为谁、解决什么问题、做完之后什么变得可能。不要写「本文档描述了…」。>

## 1. 背景与目标

### 1.1 问题陈述与现状

> 先从用户视角说清「谁正被什么阻碍、造成什么影响」,再写现状与为什么是现在。不要把待做功能换个语序当成问题。有数据放数据（多少人/多少次/多少时间）。
> 调查中读到的现状带路径或出处，与用户假设冲突的地方在这里说清楚。

### 1.2 目标（**终局**、可度量的结果，3–5 条封顶）

> 写这块能力**做完之后**要达成的结果，不是「首期做到哪」。分期在 §7。

- G1 <结果句，带判据。例：租户管理员无需联系运维即可完成 X，全流程 ≤ 3 步>
- G2 …

### 1.3 非目标（逐条给去向）

| # | 不做什么 | 为什么 / 去向 |
| --- | --- | --- |
| N1 | <最容易被认为「顺手也该做」的相邻功能> | <另立项 / 属于别的产品域 / 明确永远不做及理由 / 依赖的底座本身另立项> |

> 这张表是评审的挡箭牌。凡会被问「那 X 呢」的，都要提前出现在这里。
> ⚠️ **去向里不许出现「二期 / 后期再做」**——那是分期，不是非目标。凡属于这块能力终局蓝图之内的，写成 FR/NFR 进 §3，再到 §7 排到靠后的期次去。

## 3. 需求条目

> 每条一小节。SPMS key 在创建后回填;**需求标题和实体引用必须使用真实 FR/NFR key**。`R#` 不是需求编号,只在「承接」和 §6.1 作原始诉求来源标识。
> FR 与 NFR 分开成组（对应 SPMS 的「功能性 / 非功能性」分组）。
> **每条按完整能力写**——验收标准覆盖这条能力**做完**该有的全部断言,不写「本期版本」。「分期」行是 §7 定稿后回填的,不是写作时先定的。

### FR-<N> <标题（动宾短语，一眼看出用户能做什么）>

- **优先级**：`urgent|high|medium|low|none`（紧急度）　**重要度**：`critical|high|medium|low|none`（与紧急度正交，两个都给）
- **承接**：原始诉求 R<#> · 目标 G<#> · 场景 S<#…>
- **分期**：<P#｜跨期写「P1 / P2，**终验期 P2**」>（§7 定稿后回填，与 §7.2 逐字一致）
- **背景**：<为什么需要这条，一两句>
- **行为**：<谁在什么场景下能做什么。用户可感知的能力，不写实现。**按完整能力写**，不写「本期先只做…」>
- **边界**：<**永久**不含什么；容易被误解的地方在这里堵死。「这期先不做」不写这里，写 §7>
- **依赖**：<依赖别的 App/底座的写明；「未就绪则降级为 X」>
- **验收标准**（→ SPMS `acceptanceCriteria`,一行一条、无 markdown 语法;断言用户/外部系统可观察的业务结果,不断言内部实现;**跨期需求逐行加 `[P#]` 前缀,单期需求不加**）：

```
<角色>在<条件>下<动作>后，<系统必须怎样，带数字>
<边界条件：为空/超限/无权限时的行为>
<可观测的落点：列表出现该行 / 通知送达 / 审计留痕>
```

> **仅跨期需求**：这条抄进 SPMS `description` 的开头（SPMS 里的读者看不到 PRD，PRD 条目里也留一份）——
> `> **分期与终验**：本需求跨 P1 / P2 交付，**终验期 = P2**。P1 完成后请停在交付段（已提交 / 可测试），**不要转「已上线」**——「已上线」是整条需求的验收，不是某一期的完工。`

- **测试用例种子**：TC-<N> <一句话标题>；覆盖 S<#> / 验收第 <#> 行；<还需要几条覆盖什么>

### NFR-<N> <标题（质量属性 + 约束对象）>

- **质量属性**（`category`）：`performance|security|usability|reliability|compatibility|maintainability`
- **优先级**：`…`
- **承接**：原始诉求 R<#> · 目标 G<#> · 场景 S<#…>
- **分期**：<P#｜跨期写「P1 / P2，**终验期 P2**」>（§7 定稿后回填）
- **约束**：<必须带数值与作用域。例：列表首屏 p95 < 300ms @ 单租户 1 万行；超限行为是分页而非截断>
- **验收标准**（同上格式，一行一条）：

```
<可度量的断言，含数字与测量条件>
```

- **测试用例种子**：TC-<N> …；覆盖 S<#> / 验收第 <#> 行

## 4. 约束与前提

- **用户给定的约束**：<原话来源标注「用户原话」；这是 PRD 里唯一允许出现技术选型的地方>
- **平台硬约束**：<多租户隔离 / 业务错误 200 / 列表服务端分页 / 三语 i18n / 席位与计量 / ACL 可见性——命中哪条写哪条，并说明对本期的具体影响>
- **既有决策约束**：<相关 ADR/决策记录中对用户可观察行为的约束 + 出处;不抄实现方案。无则写「无」>
- **前置依赖**：<某 App 或底座就绪与否，未就绪时的降级方案>

### 5.2 开放问题

| # | 类型 | 问题与影响 | 当前默认及理由 | 负责人 | 截止时间 |

## 7. 分期交付建议

> **全篇唯一谈交付节奏的地方**——§0–§6 一律按终局写。分期只改变顺序，**不改变需求集合**：这里不删需求、不砍验收标准、不把需求改小。
> **供参考、非约束**：期次边界不等于计划边界，一期落成一份计划、一份计划里的几个里程碑、还是与别的 PRD 的需求合并，由 dev-plan 按技术依赖判断。**唯独「终验期」不是建议**——那是「整条需求何时算完成」的事实。

### 7.1 期次总览

| 期次 | 这期上线后，哪个角色多了什么以前做不到的事 | 出口判据（引用 §3 验收原话） | 前置 |
| --- | --- | --- | --- |
| P1 | <一个能独立交付的用户价值；不是「先做后端」这类技术栈切法> | <这期覆盖到的验收标准行> | <无 / 等某底座就绪 / 等某既有 key 先上> |
| P2 | … | … | P1 |

### 7.2 分期矩阵（每条需求都要有一行，含本次更新的既有 key）

| 需求 | 来源 | P1 | P2 | **终验期** | 说明 |
| --- | --- | --- | --- | --- | --- |
| FR-37 | 本 PRD 新建 | 验收 1–2 行 | — | **P1** | 单期完成 |
| FR-38 | 本 PRD 新建 | 验收第 1 行 | 验收 2–4 行 | **P2** | **跨期**；P1 完成后不得转「已上线」，见 §7.3 |
| FR-18 | 既有 · 本次更新 | — | 补验收第 3 行 | **P2** | 只动这一行，正文不重述；本次未改变它原有的终验口径 |
| NFR-9 | 本 PRD 新建 | — | 全部 | **P2** | 依赖 X 底座就绪 |
| FR-41 | 既有 · 别的 PRD（`docs/PRD-B.md`） | 前置 | — | 不归本 PRD | P1 等它先上；本 PRD 不排它的期 |

> **「来源」标签固定用这几种**：本 PRD 新建 / 既有 · 本次更新 / 既有 · 别的 PRD（只作前置） / 既有 · 别的项目（只作前置）。
> 既有 key 必须是查重时**真命中**的（§6.1 有据），不许编号；只作前置的那些不占本 PRD 的终验期。

### 7.3 跨期需求终验登记（只列跨期的；没有就写「本期无跨期需求」）

| 需求 | 涉及期次 | 各期完成哪几行验收 | **终验期** | 首期完成后的正确状态 |
| --- | --- | --- | --- | --- |
| FR-38 | P1 / P2 | P1：第 1 行；P2：第 2–4 行 | **P2** | 停在「已提交 / 可测试」，**不转「已上线」** |

> 每条跨期需求要在**三处**都说得一样，缺一处就会有界面在说谎：① 本表；② 该需求 SPMS `description` 开头的「分期与终验」块；③ `acceptanceCriteria` 逐行的 `[P1]` / `[P2]` 前缀。
> 另：跨期需求的**版本（release）挂终验期那一版**（人工在 Web 补）——`releaseId` 是单值字段，挂首期会让版本报表把整条需求算成那一版已交付。
> ⚠️ 需求抽屉里，**该需求已关联的 Issue 全部完成**就会浮出一键「转已上线」。跨期需求首期完工时这个按钮就亮了，而需求侧**没有**「已上线」之后的第二个终态——所以终验声明必须写进需求正文，让点按钮的人先看见。

### 7.4 交给 dev-plan

- 交接单位是 **`FR-N` / `NFR-N` key 的集合**，不是整份文档。**PRD : 计划多对多**——可拆给多份计划，也可与别的 PRD 的需求合并进同一份。
- **终验期随 key 一起交出去**：逐条写明「本计划完成后 FR-38 仍停在交付段，终验在 P2」——只覆盖 P1 的计划里程碑全绿，也不代表跨期需求可以置「已上线」。
- SPMS 侧落点 `plan_create(projectId, title, requirementKeys=[…])` → `PLAN-N`；⚠️ 一个 `PLAN-N` 只能挂**同一项目**的需求。
- <若某条与另一份 PRD 的需求天然同批，点名：与 `docs/PRD-B.md` 的 FR-41 动同一块，建议合并一份计划>

## 常见毛病(自检时对照)

| 毛病 | 症状 | 改法 |
| --- | --- | --- |
| 验收标准是愿望 | 「体验流畅」「性能良好」「操作便捷」 | 换成带数字的断言;种不出 TC 就是没想清楚 |
| 需求变方案 | 出现表名/端点/库名/里程碑 | 挪到 dev-plan;PRD 只留「用户能做什么」 |
| 粒度失控 | 一条需求要 30 个 Issue,或一条需求就是一个按钮 | 拆到「一个可感知能力、3–10 个 Issue」 |
| 非目标空着 | 只有 1-2 条或直接省略 | 把评审会被问的相邻功能全列出来 |
| NFR 没数字 | 「要安全」「要快」 | 补 `category` + 数值 + 测量条件 |
| 编号错乱 | 需求标题/实体引用仍用 R1/R2,或与真实 key 混用 | 创建后回填 FR/NFR key;`R#` 只留在「承接」和 §6.1 作来源标识 |
| 角色含糊 | 通篇「用户」 | 落到租户内具体角色,并写清权限边界 |
| 领域词漂移 | 同一概念用多个词,或「账号/状态/任务」各自指多个东西 | 在 §2.1 选定规范词与定义,全篇统一 |
| 场景只写主路径 | 权限/租户/空数据/重复/状态边界没人拍板 | 用少量高信息量 `S#` 压测真正有关的边界 |
| 决策只留在对话 | 结论有了,但后来人不知道为什么 | 在 §5.1 只记录会影响范围/语义/验收的产品决策 |
| 阻塞问题伪装成默认 | 答案会改需求,但文档仍定稿/落库 | 保留在 frontier;未拍板只能交草稿,不写 SPMS |
| 追踪链断了 | 目标无需求、场景无验收、或 FR 无 TC | 补齐 §6.2,任一单元格为空都不定稿 |
| 验收盯内部实现 | 断言表/函数/内部调用次数 | 改为用户或外部系统可观察的最高业务边界 |
| 分期混进正文 | 目标/行为/边界里出现「本期先只做…」「二期再说」 | §0–§6 按终局写;所有期次安排收进 §7 |
| 非目标当分期用 | 非目标去向写「二期 / 后期再做」 | 属于终局蓝图的挪回 §3 成为 FR/NFR,在 §7 排到靠后期次 |
| 分期只盘自己 | 分期矩阵里只有本 PRD 新建的几条 | 把查重命中的既有 key、以及同期必须一起上的别的 key 一并列进来并标来源 |
| 需求被期次切碎 | 一个可感知能力被拆成 FR-A(一期) / FR-B(二期) 两条 | 合回一条,在 §7.2 标成跨期并给终验期 |
| 按技术栈分期 | 「P1 后端、P2 前端」 | 每期必须说清哪个角色多了什么以前做不到的事;说不清就并掉 |
