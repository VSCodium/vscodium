# 写作风格：去 AI 味

AI 写的技术文档有一股很好认的味道：每节一个模子、形容词堆砌、什么都「强大」「无缝」、结尾必有总结。读者一闻到这个味道，就会怀疑内容也是凑的，哪怕事实都对。

技术文档去 AI 味，方向和散文不一样。散文靠加观点、加个性、加第一人称；技术文档靠**具体、直接、可核对**：用数字代替形容词，用行为代替评价，用读者要做的动作代替空泛的介绍。参考文档不需要个性，需要的是准确和一致。

## 1. 结构的模子

AI 喜欢套公式。最显眼，先改。

**症状**
- 每节都是「引入一句 + 三点列表 + 小结一句」
- 每节结尾都有「总之」「由此可见」「这意味着」
- 每个列表恰好三条，或者条数都一样
- 文末固定来一节「总结与展望」「未来规划」「挑战与机遇」
- 「尽管 X 很强，但也面临挑战……尽管如此，X 仍然……」这种来回绕

**改法**
- 节的长短跟着内容走。有的节两句话，有的节一整页。
- 讲完就停，不给每节系蝴蝶结。
- 列表条数就是真实的条数，四条就四条，一条就别用列表。
- 删掉总结、展望式结尾。真有后续计划，写具体的：「v2.0 计划移除 `legacyAuth`，见 #123」。

## 2. 夸大和宣传腔

技术文档不是新闻稿。

**中文**：赋能、助力、打造、构建（滥用时）、一站式、全方位、多维度、全链路（非技术含义时）、极致、卓越、领先、业界一流、革命性、颠覆、重塑、引领、里程碑、具有重要意义、至关重要、不可或缺、坚实的基础、保驾护航、为……注入新活力、开启……新篇章

**英文**：stands as / serves as a testament、pivotal、groundbreaking、revolutionize、cutting-edge、world-class、best-in-class、game-changer、state-of-the-art、marks a shift、setting the stage for

**改法**：不是换个近义词，而是删掉，换成事实。删完句子不成立，说明原来就没有内容。

> 改前：本平台致力于为企业打造一站式、全方位的数据治理解决方案，助力企业数字化转型。
>
> 改后：本平台从 MySQL、PostgreSQL 和 Kafka 采集元数据，按表和字段记录血缘，字段变更时通知下游负责人。

## 3. AI 高频词

单独出现一次不算问题，扎堆出现就是味道。

### 中文

| AI 常用 | 改成 |
|---|---|
| 旨在、致力于 | 直接说做什么：「用于」「负责」，或者删掉 |
| 扮演着……的角色、发挥着……的作用、起到……作用 | 「是」「负责」「用来」 |
| 强大的、丰富的、灵活的、高效的 | 删掉，或者给出具体能力、数字 |
| 无缝集成、无缝衔接 | 说清怎么集成：「通过 Webhook 推送」 |
| 显著提升、极大地提高、大幅优化 | 给数字：「P99 从 800 ms 降到 120 ms」；没有数字就删 |
| 深入探讨、全面解析、一文读懂 | 删掉，直接开始讲 |
| 核心、关键（一段里出现多次） | 留一个真正核心的，其余删 |
| 生态（非技术含义）、闭环、抓手、底层逻辑、颗粒度、沉淀、打通 | 说具体的东西 |
| 开箱即用 | 确实零配置可用才写，否则写需要哪些配置 |
| 高性能、高可用、高扩展 | 有测试数据或部署设计支撑才写，并给出依据 |

### 英文

| AI 常用 | 改成 |
|---|---|
| delve into | look at，或者删掉 |
| leverage、harness、utilize | use |
| seamless、seamlessly | 说清怎么连 |
| robust、comprehensive、powerful | 删掉，或给具体能力 |
| streamline | simplify、cut steps |
| navigate（比喻） | handle、deal with |
| landscape、realm、ecosystem（非技术） | 删掉或说具体领域 |
| myriad、plethora | many |
| facilitate | help、let |
| empower | let、allow |
| tapestry、testament、paradigm shift | 删掉 |

## 4. 句法层面的习惯

**绕开「是」**：「作为……而存在」「扮演着……的角色」「构成了……的基础」扎堆出现，就改回「是」「有」「负责」。英文的 serves as、stands as、functions as、boasts 同理。

**空洞的尾巴**：句子结尾挂一个「从而……」「进而……」「体现了……」「彰显了……」「为……奠定了基础」，英文是 highlighting、underscoring、ensuring、fostering。删掉，或者拆成单独一句并给出依据。

> 改前：该模块采用事件驱动架构，从而实现了各服务之间的解耦，进而提升了系统的可维护性。
>
> 改后：订单服务处理完支付后发布 `order.paid` 事件，库存服务和通知服务各自订阅，订单服务不直接调用它们。

**否定式排比**：「不仅……更……」「不是……而是……」「It's not just X, it's Y」。一篇文档用一次足够。

**凑三**：「高效、稳定、易用」「快速、安全、可靠」，第三个往往是凑的。真有三个就写三个，只有两个就写两个。

**同义词轮换**：AI 为了避免重复，会把同一个东西依次叫「租户」「组织」「空间」「团队」。技术文档里这是灾难，读者会以为是四个东西。一个概念一个名字，从头用到尾；和代码里的叫法对应，第一次出现时可以括号注明代码名：租户（`tenant`）。

**假范围**：「从小型团队到大型企业」「从开发到上线」，两端不在一个尺度上。直接列出具体支持的场景。

## 5. 节奏和格式

**句子长度一个样**：每句都是二三十字的中等长句，读起来像节拍器。长短交替，该短就短：「这一步不能省。」

**破折号**：中文的「——」和英文的 em dash（—），AI 用来插入戏剧性的补充说明。一篇文档里几段才出现一次还算正常；每段都有就是味道。改成逗号、句号、括号，或者拆句。检查脚本会报数量，数过再判断，不要凭感觉。

**加粗泛滥**：每段都有几个加粗词，等于没有强调。只在第一次出现的定义术语、真正的警告上加粗。

**加粗小标题列表**：

> 改前：
> - **高性能：** 系统性能得到了大幅提升。
> - **易扩展：** 系统扩展性更强。
> - **安全性：** 安全能力全面增强。
>
> 改后：查询接口加了 Redis 缓存，命中时响应从 300 ms 降到 20 ms；新增服务只需在 `services.yaml` 里注册；所有写接口加了 CSRF 校验。

参考文档里「**字段名**：说明」「**术语**：定义」这种格式是正常用法，不算。

**emoji**：新写的文档不给标题和列表加 emoji（✨🚀📝✅）。更新已有文档时，原文用了就沿用。

**英文标题的 Title Case**：有明确风格指南（AP、Chicago）时照指南；没有的话单独出现不算问题，和其他 AI 特征一起出现才算。

## 6. 含糊、填充、聊天腔

**铺垫句**：「值得注意的是」「需要指出的是」「众所周知」「不难发现」「It's worth noting」「It's important to note」。直接说那件事。

**过度对冲**：「在一定程度上」「可能会」「或许」「通常来说」堆在一起。确定的就直接说；不确定的用标记（`[INFERRED]`、`[UNVERIFIED]`），不要用含糊的措辞糊过去。

**模糊出处**：「业界普遍认为」「有观点指出」「Experts say」。给出具体来源，或者删掉。

**填充短语**：「为了实现这一目标」→「为此」；「由于……的原因」→「因为」；「具有……的能力」→「能」；「进行……操作」→ 直接用动词（「进行删除操作」→「删除」）；「in order to」→「to」。

**聊天腔**：「希望对你有帮助！」「如需进一步了解，请随时告诉我」「好问题！」「Let me know if...」。文档里一律删掉。

**开场白**：「在当今数字化时代」「随着……的快速发展」「In today's fast-paced world」。删掉，第一句直接说是什么。

**空泛结尾**：「未来可期」「让我们拭目以待」「综上所述」「总而言之」「The future looks bright」。删掉，文档讲完就停。

## 7. 连接词

AI 反复用同一批连接词：「此外」「另外」「同时」「与此同时」「首先……其次……最后」「总之」，英文是 Moreover、Furthermore、Additionally、In conclusion。

大多数时候不需要连接词，直接开始下一个意思就行，段落分隔本身就是过渡。需要的时候用真实的逻辑关系：「因为」「所以」「但是」。

## 8. 技术文档特有的毛病

- **「只需」「简单地」「轻松」「just」「simply」「easily」**：对卡住的读者毫无帮助，还让人觉得是自己笨。删掉。
- **用评价代替行为**：「性能很好」「非常安全」「使用方便」。写行为或数字：「单实例 2,000 QPS（见 `bench/README.md`）」。
- **把 README 写成产品宣传页**：开头一大段愿景，读者翻三屏才看到安装命令。
- **功能列表只有名词**：「用户管理、权限管理、日志管理」。每项写它具体让用户做什么。
- **「等」「等等」「etc.」收尾的清单**：参考文档要全，列不全就说明范围（「以下是最常用的 5 个，完整列表见……」）。
- **被动语态堆积**：「该配置会被系统读取并被用于……」→「系统启动时读取该配置，用来……」。

## 技术文档里合适的「人味」

改散文时去 AI 味常靠加观点、加第一人称、加幽默，这些在参考文档里都不合适。技术文档里真正让人觉得「这是懂行的人写的」的，是这些：

- 写出真实的坑：「第一次运行 `db:migrate` 会失败，因为 Redis 还没起；先跑 `docker compose up -d redis`。」
- 写出设计取舍：「这里没有用消息队列，因为订单量每天不到一千单，定时任务每分钟扫一次足够。」
- 教程和 README 可以用「你」直接对读者说话。
- 该下判断的地方下判断：「生产环境不要开 `DEBUG=1`，它会在响应里带上 SQL。」不写「建议谨慎考虑是否开启」。

## 该保留的

- 技术事实、具体数字、版本号
- 专有名词、产品名、代码标识符（保持原样，不翻译）
- 已有文档的结构和风格（更新时）
- 参考文档里统一的「**术语**：定义」格式
- 表格里真实就是三行的三条（不是所有三项并列都是凑数）
- 标准技术术语，哪怕看起来像流行词：「端到端测试」「高可用部署」「生态系统」在技术语境里有确切含义，有依据就可以用

## 改写示例

**README 开头**

> 改前：
> # 🚀 DataHub
> 在当今数据驱动的时代，数据治理扮演着至关重要的角色。DataHub 是一款强大的、一站式的数据治理平台，致力于为企业赋能，无缝集成各类数据源，助力企业实现数字化转型。它不仅提供了全面的元数据管理能力，更打造了业界领先的数据血缘追踪功能。
>
> 改后：
> # DataHub
> DataHub 收集数据库和消息队列的元数据，记录表和字段之间的血缘关系。上游改了字段类型时，它会找出受影响的下游表和报表，通知负责人。目前支持 MySQL、PostgreSQL 和 Kafka。

**架构文档段落**

> 改前：
> 值得注意的是，系统采用了先进的微服务架构，各服务之间通过消息队列实现了无缝的异步通信，从而显著提升了系统的可扩展性和稳定性。此外，网关层扮演着统一入口的角色，为整个系统提供了坚实的安全保障。
>
> 改后：
> 系统拆成 6 个服务，都挂在 `gateway` 后面。网关负责校验 JWT 并把用户 ID 写进 `X-User-Id` 请求头，下游服务只读这个头，不再自己验 token（`gateway/src/auth.ts:31`）。服务之间的异步通知走 Redis Streams，同步查询直接 HTTP 调用。

**英文 API 说明**

> Before: This powerful endpoint seamlessly enables you to effortlessly retrieve comprehensive user information, leveraging our robust caching layer.
>
> After: Returns one user by ID. Responses are cached for 60 seconds; send `Cache-Control: no-cache` to bypass.

## 快速自检

命中 5 条以上，说明需要再改一遍：

- [ ] 第一段没有直接说这是什么、给谁用
- [ ] 出现 3 个以上第 2、3 节里的词
- [ ] 有「值得注意的是」一类的铺垫句
- [ ] 每节结构一样，或者每节都有小结
- [ ] 结尾有总结、展望
- [ ] 「不仅……更……」「不是……而是……」出现两次以上
- [ ] 破折号每段都有
- [ ] 加粗小标题列表
- [ ] 标题或列表有装饰性 emoji
- [ ] 同一个概念用了两个以上的名字
- [ ] 用形容词评价性能、安全、易用，没有数字或行为
- [ ] 出现「只需」「轻松」「简单地」
- [ ] 有聊天腔（「希望对你有帮助」）
