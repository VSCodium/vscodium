# 架构文档

目标是一份可以直接交给新工程师的文档：覆盖整个系统，难的部分讲得够深，而且每个结论都能追到本地文件，所以读者敢信。它属于 Diátaxis 里的「解释」加一部分「参考」：讲清系统怎么搭起来、为什么这样搭，同时给出可查的清单（技术栈、命令、目录、运行面）。

## 范围：整个仓库还是一个子系统

- 用户说「这个仓库」「整个系统」：写全仓架构，按下文完整结构。
- 用户指定了一个服务或模块（monorepo 里的一个 app）：以它为主体，结构照用，但「系统上下文」要画出它和仓库里其他部分、外部服务的关系；和它无关的部分不写。
- 仓库特别大（几十个服务）：先写全局地图（上下文图 + 容器图 + 每个服务一行），深挖只挑两三个最关键的子系统，其余在文末列为「未覆盖」，不要每个都浅浅写一段。

## 工作方法

1. **锚定快照**：remote（去掉凭据）、分支、HEAD 提交、版本号、许可证，写进文档开头的「快照信息」表。
2. **先识别，不假设**：读 manifest、任务脚本、CI 配置、仓库里给 agent 或贡献者看的文档（`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING`、`docs/`）。技术栈和命令以这些为准。
3. **先铺广度，再挖深度**：先建立全仓地图（技术栈、入口、目录、运行面），再挑两三个最难的子系统深挖。
4. **边写边核对**：引用哪个文件哪一行，就打开读那一行。没有依据的结论比空着更糟。

## 文档结构

默认写成**一个** Markdown 文件，按下面顺序。按项目实际调整标题：CLI 工具没有「前端」，就把那一格换成对这个项目重要的东西，但保留整体形状和核对纪律。

### 1. 快照信息

| 项 | 值 |
|---|---|
| 仓库 | remote URL（已去凭据） |
| 分支 / 提交 | `main` / `a1b2c3d`（日期） |
| 版本 | manifest 里的版本号 |
| 许可证 | `LICENSE` 里的类型 |

### 2. 这是什么

一段话：系统做什么、给谁用、在更大的体系里处于什么位置。引用 README 或入口代码。

### 3. 技术栈

表格，列「层 | 技术 | 版本 | 依据（文件:行）」。区分生产依赖和开发工具。

### 4. 入口

后端服务、前端应用、CLI、后台任务、定时任务，各自从哪个文件启动、怎么启动。

### 5. 命令与验证清单

列「命令 | 用途 | 依据」，覆盖：安装、构建、启动、测试（包括怎么只跑一个测试）、lint、格式化，有的话再加类型检查、端到端测试、契约测试、数据库迁移、种子数据。每条命令都要能在任务脚本、manifest 或 CI 配置里找到，找不到的标 `[UNVERIFIED]`。

再写 CI：哪些 workflow、什么时候触发、跑哪些命令。CI 是否是**合并前必须通过的检查**（分支保护、required status check）通常看不出来，这是在代码托管平台上手动配置的；问用户，或者标 `[UNVERIFIED]`。

### 6. 目录结构

每个主要目录一行说明用途。monorepo 按 workspace 分别列。路径别名（`tsconfig.json` 的 `paths`）先映射成真实路径再写。

### 7. 部署与运行面

所有「运行时」版本被钉住的地方：容器基础镜像（`Dockerfile` 的 `FROM`）、`docker-compose` 里的服务镜像和版本、CI runner 镜像和 `setup-*` 版本、`engines` / `.nvmrc` / `.tool-versions`、serverless 运行时、数据库 / 缓存 / 消息队列的镜像 tag。每项带出处。构建用的版本和运行用的版本不一致时，在这里指出来。

### 8. 数据与存储

有哪些数据库、各自存什么、谁读谁写、迁移怎么管理、有没有多租户隔离、缓存和消息队列的用途。

### 9. 架构蓝图

- **系统上下文图**（C4 第一层）：系统和用户、外部系统的关系。
- **容器图**（C4 第二层）：系统内部可以独立部署或运行的单元（服务、前端、数据库、队列）以及它们之间的通信方式。
- **一个典型请求的完整链路**：从入口到存储再返回，挑最有代表性的一个（登录、下单、核心业务操作）。
- **分层与依赖规则**：什么可以依赖什么，谁来保证（lint 规则、目录约定、代码评审、构建工具）。没有强制手段的，如实写「靠约定」。
- **横切关注点**：表格，列「关注点 | 实现位置 | 依据」，覆盖鉴权、配置、日志、指标 / 链路追踪、密钥、错误处理、特性开关、国际化，有哪些写哪些。
- **推断出的架构决策**：从代码和文档里还原关键决策，每条写「决策、可能的原因、带来的约束」，标 `[INFERRED]`，有明确文档依据的除外。
- **治理机制**：CI 门禁、代码生成校验、CODEOWNERS、评审规则、兼容性规则（前后端分开发布、存储双向兼容、protobuf 只增不改之类）。这些是新人最容易踩的规矩。

### 10. 子系统深挖

挑两三个最复杂或最关键的子系统：新人最难看懂的那部分，例如调度引擎、插件加载流程、状态机、权限计算、计费。每个写：

- 内部结构和关键类型
- 生命周期或状态流转
- 数据怎么流动
- 一张小图（时序图或状态图）
- 带行号的引用

这部分是架构文档和目录清单的区别所在，值得多花时间。

### 11. 新人指南

- 加一个功能要动哪些地方，按顺序列出（路由、校验、服务、数据库迁移、前端、测试、文档）。
- 常见的坑：测试默认 watch 模式、构建很慢、生成的代码要提交、pre-commit hook 会改文件、本地要先起哪些服务。每条带出处。

### 12. 依赖健康（可选）

已经停止维护或到了生命周期末期的运行时、框架、基础镜像、库。按实际情况标 `[INFERRED]` 或 `[UNVERIFIED]`，不要凭印象断言某个版本已经 EOL。

### 13. 可信度评估

表格，列「主题 | 可信度 | 说明」，可信度取「高 / 推断 / 未验证」。读者据此知道哪些可以直接信，哪些要自己再查。

### 14. 依据文件

文档依赖的关键本地文件，每个一行说明它证明了什么。

## 图怎么画

按 SKILL.md 的「出图」一节先探测 archify。架构文档里常用的图和对应的 archify 类型：

| 图 | archify 类型 | Mermaid 兜底 |
|---|---|---|
| 系统上下文图 | `architecture` | `flowchart LR` |
| 容器图 / 部署拓扑 | `architecture` | `flowchart` 加 `subgraph` 表示边界 |
| 典型请求链路 | `sequence` | `sequenceDiagram` |
| 子系统状态机 | `lifecycle` | `stateDiagram-v2` |
| 数据管道、事件流 | `dataflow` | `flowchart LR` |
| 业务流程、发布流程 | `workflow` | `flowchart TD` |

一份全仓架构文档一般三到五张图：上下文图、容器图、一条请求链路，再加深挖子系统里各一张。图里出现的每个组件，正文里都要有对应的文字说明。

## 让文档可信的几条习惯

- **每个非显而易见的结论都引用本地路径**，钉住具体东西时带行号（`pkg/server/server.go#L39-L41`）。路径相对仓库根，方便点击。
- **如实标记不确定**：推理出来的标 `[INFERRED]`，转述未核实的标 `[UNVERIFIED]`。
- **矛盾要裁定**：manifest 写的版本和代码里的不一致，读代码定下真实答案，写一句「已核对：……」说明依据。不要把矛盾原样丢给读者。
- **写出兼容性和发布节奏的规矩**，这是新人最容易违反的。
- **用精确数字**：「73 个 service 包」「89 个 workflow 文件」（来自目录统计），不写「很多服务」。

## 范围控制

文档只写这份 checkout 里看得到的东西。很容易越写越远：相关产品、README 里的宣传、兄弟仓库。除非在磁盘上看得到，否则不写；确实需要提的，明确标出来源不是本地代码。读者要的是**这个代码库**被如实记录下来。
