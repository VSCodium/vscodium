# 用户手册、教程与操作指南

读者是用产品的人，不是写代码的人：业务用户、管理员、运营，或者部署维护系统的运维。他们不关心代码在哪，只关心「我要做 X，该点哪里、填什么、会发生什么」。但手册里的每句话仍然要从代码里核实，因为界面上的按钮名、字段限制、权限规则都写在代码里，凭印象写的手册会和产品对不上。

## 先定读者和文档类型

| 读者 | 典型文档 | 语气 |
|---|---|---|
| 第一次用的业务用户 | 快速上手教程 | 一步一个结果，不讲原理 |
| 日常使用者 | 按任务组织的操作指南 | 直接给步骤 |
| 管理员 | 配置与权限指南 | 讲清每个设置的影响范围 |
| 运维 | 部署、升级、备份、故障处理手册 | 命令精确，写清前置条件和回滚方式 |

不同角色看到的界面和能做的事不同。按角色区分章节，或者在每个操作开头写明「需要的角色」。

## 从代码里取事实

| 要写的 | 去哪里找 |
|---|---|
| 页面和菜单的名字、入口路径 | 前端路由配置、导航 / 菜单定义、页面组件 |
| 按钮、字段、提示文字的**原文** | 国际化文件（`locales/`、`i18n/`、`messages/`）；没有 i18n 就看组件里的字面量。界面文字要和产品完全一致，不要意译 |
| 字段是否必填、长度、格式、取值范围 | 前端表单校验和后端校验 schema，两边不一致时以更严的为准，并告诉用户这个不一致 |
| 谁能做什么 | 权限 / 角色定义、路由守卫、后端鉴权中间件 |
| 操作之后会发生什么 | 后端 handler：状态变化、通知、邮件、审批流转 |
| 状态和流转规则 | 状态枚举、状态机代码 |
| 报错提示和原因 | 错误码表、i18n 里的错误文案、抛出错误的地方 |
| 数量限制、配额 | 常量、套餐配置、租户设置 |

写之前可以在交付说明里列出「手册依据的代码位置」，但手册正文里不放文件路径和行号，读者用不上。

## 手册结构

按 Diátaxis 分成几块，各写各的，不要在教程里插长篇解释，也不要在参考表里夹操作步骤：

1. **概述**：这个产品或模块能帮你做什么，适合谁用，一两段话。列出主要功能，每项一句话。
2. **快速上手（教程）**：带新用户完整走通一件最典型的事，从登录或打开页面开始，到看到结果为止。只走一条路，不讲分支。
3. **操作指南**：按任务组织，标题用动词开头，写用户要做的事：「提交工时」「审批请假」「导出月度报表」，不用「工时模块介绍」。每个任务独立成节，读者可以直接跳过去看。
4. **参考**：字段说明表、状态说明表、角色权限表、限制与配额。
5. **常见问题与故障排查**：从错误提示反推，写「看到 X 提示 → 原因 → 怎么办」。只写代码里真实存在的错误，不编造问题。

小产品可以合并成一篇；功能多的按模块拆成多篇，加一个目录页。

## 写步骤的规矩

- 一步一个动作，用祈使句：「点击「提交」。」不写「用户可以通过点击提交按钮来完成提交操作」。
- 界面文字用「」括起来（英文文档用 **粗体**），和产品上的文字一字不差。
- 路径写全：「进入「设置」→「团队成员」」。
- 关键步骤后写预期结果：「页面顶部出现「已提交，等待审批」。」读者靠它确认自己没走错。
- 有前置条件的写在最前面：需要的角色、需要先完成的配置。
- 可能出错的地方就地提醒，一句话说清原因和解决办法，不要全堆到最后。
- 不写「只需」「轻松」「简单地」，对卡住的读者来说这些词没用，还让人烦。
- 字段说明写「填什么、格式、限制」，不写「请填写正确的值」。

例子：

> **提交报销单**
>
> 需要的角色：员工
>
> 1. 在左侧菜单点击「费用报销」，再点击右上角「新建报销」。
> 2. 选择「费用类型」，填写「金额」。金额最多两位小数，单笔不超过 50,000。
> 3. 在「附件」里上传发票图片，支持 JPG、PNG、PDF，单个文件不超过 10 MB。
> 4. 点击「提交审批」。
>
> 提交后报销单状态变为「审批中」，不能再修改。需要修改的话，请审批人点击「退回」。

（示例为虚构产品，只示意写法。）

## 截图和图

- 截图不能编造。仓库里已有截图，或者用户提供了，才引用。需要截图但没有的，在对应位置写 `[TODO: 截图 - 「页面名」页面，标出「按钮名」]`，交付时统一告诉用户要补哪些。
- 能在本地把应用跑起来、并且有浏览器自动化工具时，可以自己截图；截图里不要出现真实的个人信息。
- 流程类内容（审批流、提交流程）和状态类内容（单据状态流转）适合配图，按 SKILL.md 的「出图」一节处理：审批流、多角色协作流程用 archify 的 `workflow`，状态流转用 `lifecycle`；没有 archify 用 Mermaid。面向业务用户的图，节点名用界面上的叫法，不用代码里的枚举名。

## 运维手册

读者是部署和维护系统的人，要求和用户手册不同：

- 每个操作写清：前置条件、完整命令、预期输出、怎么确认成功、失败了怎么回滚。
- 命令只写在脚本、CI、部署配置里真实存在的；环境相关的值（主机名、路径）用占位符并说明从哪里取。
- 按场景组织：首次部署、升级、备份与恢复、扩容、常见故障处理、日志在哪看。
- 危险操作（删数据、重置、迁移）单独标出来，写清影响范围。
- 部署拓扑、发布流程适合配图：拓扑用 archify 的 `architecture`，发布步骤用 `workflow`。

## 自检

- [ ] 每个界面文字都和 i18n 文件或组件里的原文一致
- [ ] 每个操作写了需要的角色
- [ ] 字段限制和校验代码一致
- [ ] 教程从头到尾走得通，没有跳步
- [ ] 常见问题里的每个错误提示在代码里都能找到
- [ ] 没有编造的截图链接
- [ ] 正文没有文件路径和行号
