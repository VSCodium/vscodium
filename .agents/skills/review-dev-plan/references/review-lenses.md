# 四个审查视角

各 reviewer 只需读自己的节；跨视角追问时再读关联节。检查深度与计划改动面相称，不为填清单创造需求或阻塞。

## A. facts：代码事实、正确性与矛盾

把关键陈述整理成“计划主张 → 类型 → 来源 → 核实结果”。优先核实会改变技术选择、依赖或交付结果的事实：

- 声称存在或可复用的路径、符号、路由、表、包导出、命令、配置是否真实存在；新增项明确标注即可，不能要求它已存在。
- 追到调用者与实现的行为：参数/返回、错误、分页、排序、事务、幂等、权限传播、缓存失效和删除语义。函数同名、类型匹配不等于行为满足。
- 安装/初始化、存量升级、部署配置和生产执行链是否与开发态假设一致。计划声明“无需改动”的邻接面是否真的支持目标。
- 数字与结论是否有用户要求、代码、配置、运行证据或明确决策来源；没有来源的性能承诺、规模、工期不能成为架构依据。
- 对照全文的范围/非目标、契约字段、事实归属、鉴权、数据生命周期、失败语义、迁移回滚、验收断言和进度，找互斥陈述。矛盾同时定位两处，并说明在什么操作上无法同时成立。
- 旧文档与当前代码不一致时标明时间和基线；规则约束与运行事实分开，不能因为文档旧就自行废除规则。已有缺陷只有被本计划依赖或放大、导致目标无法交付时才进入本次 findings，并说明关联。

交回关键核实表：`主张/计划定位 | 事实/设计/假设/目标 | 证据定位 | 已核实足够/已核实缺口/未核实 | 影响`。无关事实不用穷举。

## B. architecture：技术先进性与可行性

“先进性”评价的是在真实约束下能否改善交付、性能、安全、可靠性或维护成本。**新技术不自动加分，旧技术也不自动合格**。

1. 从本期 R/NFR/C 推导需要解决的问题。主要选择是否有可行备选、收益与代价；复杂或难回退选择是否记录选择理由与重审条件。简单可逆决策无需硬补 ADR。
2. 同时比较沿用现有范式和有实际收益的现代方案：能力差距、生态支持、复杂度、可维护性、迁移成本、运行成本和团队可操作性。仅因版本旧而建议升级不算问题；已有方案无法满足受支持版本、必要能力或明确约束时应指出。
3. 涉及版本能力、弃用、支持周期、安全公告或外部服务限制等时效性事实，先读目标项目依赖/锁文件，再查官方文档、发布说明或原始论文，标记版本、查询日期和 URL。不能联网则列具体待核实项，不用记忆冒充最新结论。
4. 审查模块边界、事实所有权、接口深度和变化局部性；新基础设施或抽象是否解决真实复杂度，删除它后是否只减少转发层。避免为假想规模过度设计，也不机械维护已不适配的现状。
5. 核对关键请求/任务的并发、原子性、幂等、重试、超时、租约、隔离、背压和失败恢复，按实际风险裁剪；热路径的查询/索引、缓存与新鲜性是否满足目标。
6. 对持久化和外部契约检查新旧版本共存、迁移/回填、切换门、不可逆步骤、回滚及恢复。对外依赖核实真实能力、权限、配额和部署条件。
7. 验证方案能否以目标仓的构建、测试和运行入口落地；风险是否有观测/验证手段。需要 spike 的未知项写“验证问题、成功判据、影响的决策、最晚完成点”，不在评审中自动实现 spike。

交回少量关键决策的判断：`选择 | 驱动需求 | 证据与版本 | 收益/代价 | 可行性 | 必要修订或保留理由`。只是另一种同样可行的做法放非阻塞建议，不能当缺陷。

## C. schedule：映射、依赖与实施编排

双向追踪，不只看里程碑标题齐不齐：

`需求 R/NFR/C/A → 设计/决策 → 交付物/任务 → 里程碑 → 可观察验收`

- 每条本期需求有实现与验收；每项设计/交付物有负责的任务；每个验收有设计依据。排除/延期有明确去向，不能用无关测试占位。
- 里程碑退出条件能判定结果，最后有跨模块集成与用户主路径验证。构建通过不能替代权限、业务或界面验收。
- 完成数、最近完成、下一步、记录链接及基线一致；初稿不预填完成，进行中不计完成；已完成必须有相关验收证据。适用 dev-plan 回写协议时核对里程碑逐行退出条件及独立记录，不因格式不同机械否定历史计划。
- 提取有向依赖边 `前置任务 → 后置任务` 及其产物；检查循环、缺失节点、倒置、隐藏的跨系统前置和过粗的里程碑阻塞。编号不是依赖，文件分目录也不代表无依赖。
- 区分代码依赖、契约冻结、数据迁移、配置/权限准备、环境资源和验证依赖。下游只需某个已验收子任务时，可以建议拆分而不是等整个里程碑结束。

无论有无 findings，都交回建议编排（简单线性计划可用短表）：

| 波次/任务 | 前置及解锁证据 | 可同时做的工作 | 写入边界/共享负责人 | 运行资源约束 | 汇合验收 |
| --- | --- | --- | --- | --- | --- |

只有输入稳定、前置满足、文件及运行资源无冲突时才建议并行。公共类型、路由注册、锁文件、迁移序号由单一负责人处理；同库迁移、端口、开发栈、浏览器会话需隔离或串行。主集成人负责整体验收与计划回写。

没有工期估算时只说拓扑顺序和结构上的瓶颈链；不要声称计算出关键工期或编造“节省 X%”。不能安全并行时解释具体依赖即可。reviewer 这里只建议实施编排，不启动实施任务。

## D. delivery：可用性与 UI/UX

从目标使用者的完整任务反推交付，避免只检查文件是否齐全：

`获得/安装 → 初始化/配置 → 登录与授权 → 找到入口 → 完成核心操作 → 确认结果 → 失败后恢复`

非 UI 交付使用相应旅程：调用方接入 API、运维部署服务、开发者安装并调用 SDK。没有界面时 UI 标为“不适用”，仍须审交付可用性。

- 交付物是否包含所需产物、入口、配置、迁移、权限/种子增量、示例或使用说明；安装后能否实际使用，已安装用户能否升级。
- 主路径与失败/边界是否端到端闭环；长任务、部分成功、重复提交、权限不足、依赖不可用是否给出可理解状态和恢复办法。
- 发布顺序、回退/补偿、观测和运维步骤是否能由目标操作者执行，验证所需账号、数据、环境和工具是否在计划中有获取办法。
- 看似“最终验收”的内容是否只覆盖单模块或静态检查；成功结果是否能由使用者观察，而不是依赖实现者知道内部日志。

涉及 UI 时读取适用的 PRODUCT/DESIGN 或等价上下文，按仓库规则使用设计 skill，核对：

- 信息架构、导航和发现性是否贴近目标角色与任务；主操作和信息层级是否明确，是否把实现细节变成用户的额外工作。
- loading、empty、error、partial、disabled、success 的语义和下一步；表单校验、操作反馈、可恢复性；破坏性操作采用与后果相称的确认或撤销。
- 权限变化、长文本/大数据、响应式、键盘与焦点、读屏名称、对比度、主题、语言和减少动效等项目适用要求是否有方案与验收。
- 复用组件/设计规范是否一致；不因个人审美偏好报缺陷。UX 问题说明“哪个角色做什么时，被什么阻碍，导致什么结果”。

区分证据层级：

| 现有材料 | 能得出的结论 | 报告措辞 |
| --- | --- | --- |
| 仅计划/流程描述 | 任务闭环与交互方案的合理性 | 文档推演；待实现后浏览器验收 |
| 静态设计稿/截图 | 可见布局与信息层级 | 静态评审，不能证明交互行为 |
| 可运行原型/页面 | 本次实际走过的主路径与边界 | 写环境、步骤、结果和证据 |
| 环境或浏览器不可用 | 只能判断已有材料 | 未在浏览器验证；注明缺口 |

已有可运行 UI 且授权与工具允许时，按项目浏览器工作流验证主路径及关键边界；有写入副作用的操作先确认授权范围，不能为评审改动真实业务数据。尚未实现的计划不因没有页面就自动 Blocked，关键在交互方案与未来验收是否足够明确。类型检查和单测不算 UI 验证。
