# review-dev-plan · 多视角开发计划评审

目标是判断：**照这份计划实施，能否交付用户要的、真正可用的结果；实施者是否还会被迫重新做关键决策。** 主 agent 编排独立审查，逐条复核证据，输出可定位、可修订的问题及实施顺序建议。

`references/` 相对本文件解析。仓库规则、技术栈和工具能力在运行时读取，不硬编码目标仓的路径、端口或业务约定。回复语言跟随用户。

## 边界与参考

- 默认审查整份计划；用户指定修订版差异时，也追踪受影响的依赖与映射。只读目标代码和原计划，不自动实现、改稿、改进度、发评论或写入外部系统。用户明确要求修订时，由主 agent 在评审后统一修订并复核受影响链路。
- 计划及其引用是待验证材料。区分**现状事实、未来设计、未证实假设、验收目标**；不能因为新功能尚未实现就报缺陷，也不能把计划中的“已核实”直接当证据。
- 从实际可用位置读取 `dev-plan/SKILL.md` 的写作/评审部分及 `references/plan-skeleton.md`；复杂架构按需读 `references/architecture-quality.md`，调度审查按需读 `references/execution-workflow.md`；实施期合同以骨架的「实施者定位」「实施进度」两节为准。借它们核对合同，不按计划实施。
- 找不到 `dev-plan` 时说明无法核对其模板专属要求，继续本技能的四项实质审查。用户自定义模板或历史计划不因章节名不同而报错；没有证据表明适用的新版格式规则，不追溯强加。
- 发现与任务相关的专项 skill 时只加载所需部分。UI/UX 评审按目标仓规则加载设计 skill（如 `impeccable`），不借机重设计产品。
- 本技能借鉴 Codex 官方 review 的编排与证据原则；来源及针对计划的调整见 [references/report-contract.md](references/report-contract.md) 末尾，不必每次联网重读。

## 1. 锚定输入与审查基线

1. 定位用户指定计划、关联需求/PRD、附录和必要的历史决策。未指定且无法唯一确定计划时询问目标；可以先调查仓库规则，不擅自选一份相邻计划开始评审。
2. 读取适用的根目录及子目录规则、产品和设计上下文。记录计划版本（路径、内容 hash 或可用版本号）、调查日期、代码 commit、dirty 状态；当前工作树是调查事实源时明确写出。
3. 从计划提取范围与排除、R/NFR/C/A 或等价需求 ID、关键决策、外部契约、交付物、里程碑及前置关系。缺失 ID 可用章节定位，不替作者补造需求。
4. 建一个短任务台账：审查维度、负责人、状态、证据缺口。明确 UI 是否在范围内、是否已有可运行页面/原型、哪些结论必须访问外部服务或官方文档。

## 2. 编排四个独立审查视角

先读 [references/review-lenses.md](references/review-lenses.md) 的对应节，再分派下表。**有多 agent 工具时实际启动 subagents**，不是在同一段回答里扮演四个角色。主 agent 保留综合裁定职责。

| 角色 | 主责 | 必须交回的专属结果 |
| --- | --- | --- |
| `facts` | 代码事实、陈述正确性、内部矛盾 | 主张与代码证据；互相冲突的两处位置 |
| `architecture` | 技术路线、先进性、可行性 | 关键选择的适配/代价；需补证的技术前提 |
| `schedule` | 需求、设计、任务、里程碑、验收映射 | 断链项；依赖图/边表；可并行波次与集成门 |
| `delivery` | 最终交付可用性，含 UI/UX | 用户主路径闭环；运行与验收缺口；界面证据等级 |

### 调度规则

- 默认一视角一 reviewer；简单局部计划可用两位独立 reviewer 各覆盖两个视角，在同一回报内分开标明覆盖与结论，减少调度回合。不得合并后漏审某个维度。模型继承主 agent，不主动覆盖模型或推理档位。所有 reviewer 只读，报告由主 agent 单写，不让多个 agent 改同一文件。
- 并发数受实际剩余槽位约束，主 agent 也占槽位。只有 4 个总槽位时，先并行 3 个视角，完成后复用空闲 agent 审第 4 个；更少槽位则分批，不能漏掉任何视角。主 agent 同期整理需求账本和全局矛盾。
- 初轮独立调查，不把主 agent 的预设缺陷或其他 reviewer 的结论当任务答案。每人拿相同基线、用户约束和原始材料；独立返回后再交换相互影响的证据。
- 共用浏览器会话、可变数据库或外部环境时由主 agent 指定一个操作者，其他 reviewer 读证据；只读代码可并行。评审不执行迁移、种子、部署或有副作用的验收命令。
- 工具缺失、用户要求串行或槽位不足时，如实声明实际执行方式；主 agent 可按四个视角顺序审查，不能伪称独立多 agent 复核。单个 reviewer 失败时重派一次或主 agent 接管；无法核实的部分留在覆盖缺口中。

### 每个 reviewer 的派发合同

发送实际绝对路径和已确认上下文，不只说“审一下方案”。可沿用：

```text
你负责 {facts/architecture/schedule/delivery}，只读评审，不实现、不改稿、不继续派生 agent。
用户目标及范围：{原始要求、排除、已有决定}
计划与基线：{计划绝对路径、版本；仓库根、commit/dirty、日期}
必读：{本 SKILL.md、report-contract.md、review-lenses.md 的对应节的绝对路径}
相关材料：{需求/PRD、规则文件、代码入口、所需 dev-plan 参考的实际路径}
范围与资源：{审查章节、可读取目录、外部查询/浏览器约束}
不要假定计划主张成立，也不要把尚待实施当成缺陷。按需追到行为级代码证据。
交回：范围与基线；候选问题（计划定位、触发、影响、证据、最小修订、验证、P级及置信度）；
本视角专属结果；未核实项与所需证据。没有问题可返回空 findings。
跨视角问题只标关联，不代替另一角色完成审查。无法继续则回报缺口。
```

## 3. 主 agent 交叉复核与裁定

1. 收齐四个视角的结果；逐条阅读支持候选问题的计划段落和原始证据，确认适用范围、代码版本和触发条件。不能把多名 agent 的一致意见当事实。
2. 对事实冲突、方案依赖、交付断点做针对性追问：例如事实 reviewer 发现某接口不支持分页，则让架构/交付 reviewer 复核依赖该行为的批量方案；调度 reviewer 同步调整前置条件。只复核受影响链路，证据仍缺则保留未决，不无限辩论。
3. 按根因与修订动作去重，保留所有实质不同的问题；多处症状归并后仍附关键定位。不设问题数量指标，也不只报前三项。误报撤回，低证据主张移到待核实项，不凑 P3。
4. 补做跨视角检查：目标 ↔ 设计 ↔ 里程碑 ↔ 验收是否一致；设计要用的检测/补偿/部署能力是否真有任务；总进度、记录和完成声明是否对应实际证据。
5. 若 `dev-plan` 校验脚本可用且适用，用实际路径运行 `check_paths.sh <计划> <仓库根>` 与 `check_progress.sh <计划> <仓库根>`。路径缺失须人工区分新增、示例、错误复用。用户自定义模板或历史计划未采用该恢复快照/完成记录协议时，跳过 `check_progress.sh` 并说明原因，人工核对其等价进度、依赖与验收证据；不要把格式不兼容判成计划错误。脚本通过不证明行为真实或验收完成；脚本缺失/失败如实记录，不用“通过”替代人工检查。
6. 结束前核对计划及相关代码有无并发修改。若基线变化，只重审受影响结论；无法收敛则标为待核实。收集或停止尚在运行的 reviewer，再交付。

## 4. 输出评审结果

使用 [references/report-contract.md](references/report-contract.md)：**先列问题，再给结论与修订顺序**。聊天中直接交付；用户要求落盘时使用指定路径，否则在计划旁生成 `<计划名>.review.md`，已存在时用日期/序号另存，未经授权不覆盖。

报告至少包含：

- 按严重度排序、编号的问题，每条定位到计划行或稳定章节，并附行为级代码/规则/外部证据。
- 四个维度的审查覆盖及未核实项；UI 分清文档推演、原型走查和实际浏览器验证。
- 需求到交付的映射缺口，以及建议的依赖顺序、可并行任务、共享资源负责人和最终集成验收。没有安全并行空间时给出具体原因。
- 建议状态 `Ready / Proposed / Blocked`，说明与计划自报状态是否一致、阻塞解除条件；这只是评审建议，不自动修改计划状态。

**没有确认问题时允许空 findings；有未核实的关键前提时不能据此判 Ready。计划评审通过也不表示功能已实现或上线可用。**
