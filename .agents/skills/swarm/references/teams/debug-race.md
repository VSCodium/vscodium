# 团队模式 · 调试竞争（假设并行验证）

> 六个团队模式之一，只在命中时读这一个。

**适用**：复现困难或根因不明的 bug、多个互斥假设需要同时验证、性能劣化归因、偶发失败。

**不适用**：报错信息已经直指原因（自己修）；需要的其实是功能改动而不是归因。

---

## 机制建议

**并行后台 subagent 是默认选择**——每个假设一个调查员，独立跑，互不干扰，lead 裁决。只有在假设之间需要互相质疑、或调查要跨多轮逐步收窄时，才升级成 agent team。

---

## 角色

| 角色 | 载体 | 权限 | 职责 |
|------|------|------|------|
| **lead** | 当前会话 | — | 拆假设、分配、裁决、决定下一轮 |
| **reproducer** | `general-purpose` | 可写 `tmp/`、测试目录 | 造最小复现；给出稳定复现步骤，或证明不可复现 |
| **hypothesis-A/B/C 调查员** | `Explore`（只读） | 只读 | 各自独立调查一个假设 |
| **fixer** | `general-purpose` | `acceptEdits` | 根因确认后**唯一**动手改的人 |

---

## 顺序

```
t1 最小复现（reproducer）        ← 没有稳定复现，后面都是猜
   ↓
t2 假设 A ‖ 假设 B ‖ 假设 C 并行调查（互斥、可证伪）
   ↓
t3 lead 裁决根因（证据不足则补一轮新假设）
   ↓
t4 fixer 修复 + 回归测试
   ↓
t5 用 t1 的复现验证已修复，并复述根因链条
```

---

## 规则

1. **假设必须互斥且可证伪。** 派活前 lead 把每个假设写成「如果 X 为真，应该能观察到 Y」的形式。「可能是缓存问题」不是假设；「列表接口在缓存过期后仍返回旧数据，因为 TTL 用了创建时间而非更新时间」才是。假设不互斥，三个调查员查的是同一件事。
2. **调查员只读。** 边查边改会破坏现场，也会让另一个调查员的观察失效。想验证某个猜想，写进报告请 reproducer 或 fixer 去做。
3. **每人交三段式结论：支持证据 / 反对证据 / 判定（成立 / 不成立 / 证据不足）。** 只报支持证据的调查员没有价值——确认偏误是这类团队的主要风险，明确要求列出反对证据能压住它。
4. **鼓励互相质疑**（team 模式下）：A 发现与 B 的假设矛盾的证据时，直接 `SendMessage` 给 B 和 lead。
5. **根因确认后只留一个 fixer。** 多人同时改，事后无法判断到底是哪一处修好的。
6. **修完要留回归测试，并写出根因链条**：触发条件 → 代码路径 → 为什么之前没暴露。写不出这条链，说明根因还没找到，只是症状被压住了。

---

## 规模

3–5 人（复现者 + 2–3 个假设 + fixer，lead 兼裁决）。

---

## 常见失败

| 症状 | 处理 |
|------|------|
| 三个调查员查的是同一件事 | 派活前把假设写成可证伪的形式，检查互斥性 |
| 没有稳定复现就开工 | t1 是硬前置；不可复现时先解决复现 |
| 调查员边查边改，现场被污染 | 载体用 `Explore`（`Write`/`Edit` 被拒） |
| 报告只列支持证据 | 输出契约强制「反对证据」栏 |
| 根因没定就多手修复 | t4 只留一个 fixer |
| 修完没测试，两周后同一个 bug 回来 | t4 必须附回归测试 |
