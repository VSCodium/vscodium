# 团队模式 · 产品团队（需求设计 · 澄清 · 评审）

> 六个团队模式之一，只在命中时读这一个。

**适用**：
- 一句模糊诉求要变成可执行需求（PRD、FR/NFR、验收标准）
- 已有需求文档要评审：完整性、歧义、可测性、可行性
- 需求评审会前的准备——把各方视角的问题一次性备齐
- 需求拆分与排序、验收标准体检
- 跨角色/跨端需求的边界澄清（权限、租户、空数据、重复与超限、状态机、前置未就绪）

**不适用**：需求已定稿只差实现（→ 功能开发）；纯技术方案选型（→ 研究辩论）；只给一条需求估点（`story-points` skill 单人就够）；只把验收标准扩成成套用例（`test-plan` skill 单人就够）。

---

## 机制建议：两段式，别一上来开满编

产品工作的形态是「多轮修订 + 每轮多视角评审」，两段的最佳机制不同：

- **摸底与评审**：多个独立视角看同一份材料，彼此不需要协商 → **并行后台 subagent**（视角多时用动态 workflow 扇出更省事）
- **草稿 → 澄清 → 修订**：设计师与澄清官要多轮往返 → **agent team**（teammate 常驻，改一版不用重新解释背景）

一个硬约束决定了流程形状：**teammate 拿不到 `AskUserQuestion`，只有 lead 能问用户。** 所有澄清问题必须先汇聚到 lead、批量问一次、再把答复广播回去。让每个角色各自去问，等于让用户被问五遍——然后一个都答不上来。

## 角色

| 角色 | 载体 | 模型/effort | 权限 | 可写范围 | 职责 |
|------|------|-----------|------|---------|------|
| **lead（产品负责人）** | 当前会话 | — | — | 定稿合入 | 唯一与用户对话的人；汇聚澄清问题并批量提问；裁决分歧；合成评审结论 |
| **product-designer（产品设计师）** | `general-purpose`，或自定义 `.claude/agents/product-designer.md` | `opus`/`sonnet` + `high` | `acceptEdits` | `docs/prd/<feature>.md`（**PRD 唯一写手**） | 按 PRD 骨架产出：概述/目标/非目标 + 逐条 FR/NFR + 可断言验收标准 + TC 种子；分期建议放末尾 |
| **clarifier（需求澄清官）** | `Explore`（只读） | `sonnet` | 只读 | 不写文件，交问题清单 | 找歧义、缺口、隐含假设；构造 2–4 个高信息量业务场景压测语义与边界；问题分级并给建议默认值 |
| **stakeholder-proxy（干系人代理）** | `Explore` | `sonnet` | 只读 | 交立场报告 | 分别代入最终用户 / 运营 / 客服 / 合规 / 数据等视角，指出这份需求会让哪个角色受伤、哪句话会被误解 |
| **feasibility-reviewer（技术可行性评审）** | `Explore` | `sonnet`/`opus` | 只读 | 交可行性报告 | 对着**代码库事实**核对：现有数据模型/接口/权限能否承接、影响面、隐藏成本；结论分「可直接做 / 需先改 X / 做不到」 |
| **acceptance-reviewer（验收评审）** | `Explore` | `sonnet` | 只读 | 交验收体检报告 | 逐条验收标准判定是否可断言、可测；抓「体验流畅」这类无法成例的写法并给出改写 |
| **estimator（估点与排期，可选）** | `general-purpose` | `sonnet` | `default` | 不写 PRD | 按因子表给点数与判定依据，复核 Sprint 容量 |

> 只读评审角色用 `Explore` 最省事，但它**不加载 CLAUDE.md 与 git status**。对 feasibility-reviewer 这通常有影响（判断「能不能承接」往往要看仓库约定与当前分支状态）——这时改用自定义只读 agent，或把相关约定直接抄进提示词。

## 三轮流程

```
轮次 1 · 摸底（并行，全部只读）
  clarifier    → 歧义与缺口清单 + 压测场景 S1…Sn
  feasibility  → 代码现状盘点（能承接什么、要先改什么）
  stakeholder  → 各角色诉求与受伤点
        ↓
  lead 合成一张「澄清问题单」（阻塞级 ≤8 条），用 AskUserQuestion 一次性问用户

轮次 2 · 成稿
  product-designer → PRD 草稿（吃进轮次 1 结论 + 用户答复）
        ↓
  acceptance-reviewer → 验收标准体检
        ↓
  product-designer → 修订

轮次 3 · 评审定稿（并行 fan-out）
  feasibility / stakeholder / acceptance 三视角同时评审定稿候选
        ↓
  lead 合成决议（通过 / 有条件通过 / 打回）
        ↓
  product-designer 定稿 → lead 问用户是否接 dev-plan / 估点 / 出用例
```

## 协作规则

1. **PRD 只能有一个写手。** 评审者一律输出独立报告（`docs/prd/reviews/<feature>-<role>.md`）或把结论作为收尾消息发回，**不许直接改 PRD**。两个理由：多 agent 同改一份文档必然互相覆盖；更关键的是，评审意见一旦被别人「顺手改掉」，就失去了「谁提的、为什么提、最后怎么处置」的追溯链——而这条链正是需求评审的价值所在。合入由 designer 或 lead 统一做。
2. **澄清问题要批量、分级、可回答。** 一次交一张清单，每条标明「阻塞设计 / 影响验收 / 可后置」，并给出**建议默认值**。这样用户没空逐条回答时，也能按默认值推进，而不是整队卡住。阻塞级控制在 8 条以内——问 30 个问题的结果是一个都得不到回答。
3. **不许替用户决定。** 每个角色的提示词里都写明：不确定就回传 lead。产品团队最隐蔽的失败，是某个 agent 自己脑补了用户意图，然后整份需求建立在那个想象上。
4. **评审要有判定，不要有感想。** 固定结构：结论档位（通过 / 有条件通过 / 打回）+ 逐条问题（引用原文 → 为什么是问题 → 建议改法）。「建议再考虑一下」这类无法执行的条目不要写。
5. **代码事实优先于产品想象。** 可行性评审必须引用真实文件路径、接口名、字段名，不许凭常识判断「这个应该好做」。产品团队最贵的错误是承诺了一个代码库承接不了的需求。
6. **正文写终局，分期放末尾。** PRD 正文按目标全景写，分期交付建议只在末尾一次给出并逐条标明终验期——否则阶段交付会被误记为整条需求已完成。

## 与本仓其他 skill 的联动

`skills` 字段对 teammate 不生效，所以要**在提示词里点名让它用**，并把关键约定抄进去：

| skill | 谁用 | 提示词里要交代的事 |
|-------|------|------------------|
| `prd` | product-designer | PRD 骨架、FR/NFR 编号与验收标准写法、SPMS 写入口径 |
| `story-points` | estimator | 四轴因子表、复现性要求（同输入同输出）、写回 `plannedPoints` 前需 lead 同意 |
| `test-plan` | acceptance-reviewer | 「标准 → 用例」映射；不得覆盖或改写 PRD 种下的 TC 种子 |
| `dev-plan` | 定稿后由 lead 触发 | 需求定稿是 dev-plan 的前置输入 |

---

## 规模

- **最小可用 3 人**：lead + product-designer + clarifier
- **标准 5 人**：再加 feasibility-reviewer + acceptance-reviewer
- **完整 6–7 人**：再加 stakeholder-proxy + estimator

宁少勿多：产品团队的产出是文档，多一个视角就多一份要合成的报告，而 lead 的合成能力才是瓶颈。

## 常见失败

| 症状 | 根因 | 处理 |
|------|------|------|
| PRD 被改得面目全非，没人知道哪句是谁改的 | 多个评审者有写权限 | 收回写权限，只留 designer 一个写手 |
| 用户被反复追问，最后放弃回答 | 各角色各自提问 | 全部汇聚到 lead，一次问完 |
| 验收标准写着「体验流畅」「性能良好」 | 没人做可测性体检 | acceptance-reviewer 的核心职责，要求改写成可断言形式 |
| 需求写得很完整但代码库承接不了 | 没对着代码核对 | feasibility-reviewer 必须引用真实路径与接口 |
| 评审报告全是「建议关注」 | 输出契约没定判定档位 | 提示词里固定档位与字段 |
| 澄清官一次抛 30 个问题 | 没有分级与上限 | 阻塞级 ≤8 条，其余标「可后置」并给默认值 |
| 定稿后团队散去，需求没人接 | 流程没写下一步 | lead 定稿后主动问是否进 dev-plan / 估点 / 出用例 |
