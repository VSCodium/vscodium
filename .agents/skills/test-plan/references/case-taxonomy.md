# 用例分类法与写入契约

> 这份文件回答四个问题:**分几类、怎么映射、怎么查重、怎么写入。** 每条规则都写成可核对的形式——"覆盖得够不够"要能被人在一分钟内比对出来。
>
> 文中的 SPMS 字段/返回体形状是**平台契约**(在门户仓内核实过,别去外部 repo 找源码);§7 的完整样例取自门户仓的一条历史需求,只作写法示范。

## 1. 四类覆盖(每类 ≥1 条)

| 类 | 问什么 | 本平台的常见落点 |
| --- | --- | --- |
| **正常路径** happy | 按需求设计的走法,输入合法、权限齐备,系统给出预期结果 | 主流程走通;列表/详情显示正确;写入后能读回 |
| **边界** boundary | 极值、空值、越界、截断、状态临界 | 空列表/空状态;分页最后一页与 `hasMore`;上限值(如单批 100 项、`pms_search` 50 条);超长文本;`null` 与 0 的区别;时间窗刚好到点 |
| **权限** authz | 换一个身份做同一件事,该拒的拒、该看不见的看不见 | 未授权成员 → 拒绝**且按钮不可见**;跨项目/跨租户越权;服务账号与用户身份的差异;令牌能力不足 |
| **并发** concurrency | 两个动作同时发生 / 时序窗口内发生 | check-then-write 竞态;同一实体并发写(恰一成功);缓存 TTL 窗口内的失效时序;重复提交的幂等性 |

**每类至少一条,四类都要有。** 一条用例可以同时属于两类(如"越权且并发"),但**计数时只算主类**,并在汇报里注明。

⚠️ 被测系统属 XGENT 平台系(门户/微应用)时,两个平台口径写断言容易踩(其他系统按它自己的 API 约定写):

- **业务失败一律 200 + 错误体**(HTTP status 只表传输层)。所以权限类用例的 `expected` 要写「响应体 `code === 'FORBIDDEN'` / 按钮不可见」这类**可观测判据**;只有未登录/未授权/传输层故障才写 4xx。
- **多租户隔离**是全局硬约束:凡涉及"看得见/看不见"的需求,权限类里应有一条**跨租户**用例。

## 2. 映射表格式(覆盖率的唯一凭据)

产出必须包含这张表,一条 AC 一行:

```
| AC | 验收标准(摘要) | 用例 | 类 |
| AC1 | 授予「产品经理」后可建改删目录与需求;未授权 403 且按钮不可见 | TC-201 / TC-202 | 权限 / 正常路径 |
| AC3 | 升级后矩阵可见 5 action + 4 模板;既有授予不受影响 | TC-205 | 边界 |
| AC6 | 操作体验流畅 | ⛔ 无法成例 | — |
```

- **每条 AC 至少一个用例 key**;
- **`prd` 种下的种子**也进表(指向它的既有 key,不新建);
- **空格 = 覆盖有洞**,交付前自己先扫一遍;
- 覆盖率**没有自动断言**(需要语义判断),这张表就是人工核对的依据。

## 3. 查重口径(与 `prd` skill 共用,不许各写一套)

```
1. testcase_list(requirementKey='FR-x', limit=200)
2. 只要 hasMore === true 就继续 offset += 200 翻页,直到 hasMore === false
3. 把既有用例的 title 全部收集起来,逐条与待建标题做语义比对
4. 语义等同 → 不建,记入「跳过」清单(给出既有 key)
```

- **不翻页的查重是假的**:`testcase_list` 缺省只给 50 条、上限 200。
- 跨需求确认用 `pms_search(具体词)`,**上限 50 条**——泛词(如"用例""权限")会被截断,截断后的"没查到"不是"不存在"。
- **保证边界**(与 SKILL.md 第 1 步一致):服务端已对**带 `requirementKey`** 的 `testcase_create` 做 `(需求, 标题)` **字面幂等**(含并发,命中返既有行并置 `deduped: true`,平台契约)。仍不保证的是:① 不带 `requirementKey` 的创建;② Web 页面手工建同名;③ **语义等同但字面不同**的标题——第 3-4 步的语义比对只能靠你,这正是预查不可省的原因。

## 4. 写入契约(逐字段)

| 字段 | 传什么 | 说明 |
| --- | --- | --- |
| `projectId` | 必填 | 从 `requirement_get(...).projectId` 取,别问用户 |
| `title` | 必填 | 一句话说清"验什么",能被人在列表里一眼分辨 |
| `requirementKey` | **必传** | 如 `'FR-141'`;不传 = 孤立用例,映射关系丢失 |
| `status` | **显式传 `'draft'`** | 枚举只有 `draft` / `active` / `deprecated`;**转 `active` 是人的动作** |
| `result` | **不传** | `testcase_create` **没有这个入参**;`untested` 是 DB 默认值 |
| `priority` | 可选 | `urgent`/`high`/`medium`/`low`/`none` |
| `preconditions` | 可选 | 前置身份、数据、开关 |
| `steps` | 建议 | **一行一步**,带编号;写"点哪里/调哪个接口/传什么" |
| `expected` | 建议 | **可观测判据**:看到什么、返回体里哪个字段等于什么、状态变成什么 |

**写完断言返回体**(TC 的 DTO 形状,平台契约):

```
id === 'TC-<n>'            ← DTO 的 id 就是展示 key
requirementId === 'FR-x'   ← DTO 里回填的是需求的 key,不是 UUID
status === 'draft'
result === 'untested'      ← 服务端默认值,不是你传进去的
```

## 5. 可断言性判据(什么叫"无法成例")

一条验收标准**至少要能回答**:谁 + 在什么前置条件下 + 做什么 → **系统必须怎样(可观测)**。

缺最后一项就是无法成例。典型信号:

- 只有形容词:流畅 / 友好 / 良好 / 稳定 / 合理;
- 有数值但没口径:「要快」「响应及时」(没有 p95/样本量/数据规模);
- 有行为但没判据:「支持导出」(导出什么格式?成功的标志是什么?)。

产出格式固定:

```
AC<n>「原文摘要」→ ⛔ 无法成例
   缺:<缺什么——可观测判据 / 数值口径 / 成功标志>
   建议改写:<一句可断言的写法>
```

**这不是失败,是这个 skill 最有价值的产出之一**——它把不合格的验收标准挡在开发之前。

## 6. 数量软上限

- 目标密度:**每条 AC 1–2 条用例**,再补齐四类缺口;
- **软上限 12 条 / 需求**。超过就停下来报出:「按 AC 数应产出 N 条(超过软上限 12),请确认全建 / 只建哪几条」;
- ⛔ **不静默截断**——悄悄少建几条,"已覆盖"就成了假象。

## 7. 完整样例(FR-141,5 条验收标准)

需求:「SPMS 角色与职能:对接平台权限管理,非租户管理员可管理产品和项目」。验收标准逐条编号后:

```
AC1 普通成员被授予「产品经理」角色后,可建/改/删产品线/产品/版本/需求;未授权成员同操作返回 403 且按钮不可见
AC2 无任何角色的成员被设为项目 A 负责人后,可编辑 A、管 A 的 Sprint 与需求;对项目 B 同操作仍 403
AC3 已安装租户升级后 /admin/roles 矩阵可见 5 个新 action 与 4 个职能模板;租户自定义角色的既有授予不受影响
AC4 MCP(PAT)链路与 Web 同闸:owner 无角色时需求写被拒,授角色后 ≤60s 内生效
AC5 verify-acl / verify-catalog / verify-assignments / verify-mcp 套件全绿并纳入 verify:all
```

产出 7 条用例(≤ 软上限 12),四类齐备:

| # | 标题 | 类 | 覆盖 |
| --- | --- | --- | --- |
| 1 | 授予「产品经理」角色后可建改删目录与需求 | 正常路径 | AC1 |
| 2 | 未授权成员建产品线被拒且入口按钮不可见 | 权限 | AC1 |
| 3 | 项目 Lead 在自己项目内放大生效、对他项目仍被拒 | 权限 | AC2 |
| 4 | 升级后角色矩阵出现 5 action + 4 模板 | 正常路径 | AC3 |
| 5 | 升级后租户自定义角色的既有授予逐条不变 | 边界 | AC3 |
| 6 | 授权/撤权在实时底座 60s 窗口内的生效时序(撤权后 ≤60s 失效,窗口内 fail-closed) | 并发 | AC4 |
| 7 | 四支 verify 套件在 verify:all 中全绿 | 正常路径 | AC5 |

映射表:**AC1→1,2 · AC2→3 · AC3→4,5 · AC4→6 · AC5→7 —— 无空缺。**
四类计数:正常路径 3 / 边界 1 / 权限 2 / 并发 1 —— **每类 ≥1。**

用例 6 的写法示范(`expected` 是可观测判据,不是"应该正常工作"):

```
preconditions: PAT 令牌 owner 在门户侧已被授予「产品经理」角色;spms MCP 可达
steps:
  1. 用该 PAT 调 requirement_update 改一条需求标题 → 记录结果
  2. 在门户 /admin/roles 撤销该 owner 的角色
  3. 立即(<60s)重复第 1 步 → 记录结果
  4. 等待 > 60s 后再次重复第 1 步 → 记录结果
  5. 期间令门户不可达,重复第 1 步 → 记录结果
expected:
  1 成功;3 可能仍成功(实时底座缓存 TTL ≤60s 的残余窗口,属预期);
  4 被拒(权限不足);5 整面 503(fail-closed,不得因门户不可达而放行)
```
